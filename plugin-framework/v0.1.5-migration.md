## 一、变更总览

v0.1.5 是 DSH 的第二次重大架构升级。以下表格总结了所有可能影响插件的变更：

| 变更维度 | 影响级别 | 需要主动适配？ | 见下文 |
|---|---|---|---|
| Token Meter API 扩展 | 🟡 中 | 仅使用 `measure()` 的插件需要适配 | 第二章 |
| Permission Presets 统一服务 | 🟡 中 | 直接调用 `setSandboxMode` / `setApprovalPolicy` 的插件需要适配 | 第三章 |
| Inbox 从独立服务到投影 | 🔴 高 | 使用 `ctx.inbox` 的插件必须迁移 | 第四章 |
| LLM Adapter 新增 4 方法 | 🟢 低 | 不强制；新方法有默认实现 | 第五章 |
| Sidebar Slot 完全重写 | 🟡 中 | 自定义 Sidebar 插件需要重新适配 slot | 第六章 |
| Session V3 surface node | 🟡 中 | 直接读取 session 数据的插件需要适配 | 第七章 |
| 子代理目录 / 模型路由 | 🟢 低 | 使用 workflow / 子代理编排的插件可选适配 | 第八章 |

**快速判断**：如果你的插件只使用了 `ctx.permissionPresets.set()` 和 `ctx.tokenMeter.measure()` 这两个核心接口，基本不需要改动。下面的每一章详细说明了每个变更的影响范围、迁移路径和代码示例。

## 二、Token Meter API 扩展

### 2.1 变更内容

`ctx.tokenMeter` 在 v0.1.5 从 **3 方法扩展到 7 方法**，其中 4 个为新增：

| 方法 | 0.1.0-rc.5 | 0.1.5-rc.2 | 说明 |
|------|-----------|-----------|------|
| `estimateMessage(message)` | ✅ | ✅ | 保留，功能不变 |
| `measure(session, requestHeader?)` | — | 🆕 | **新增** — 核心测量 API |
| `estimateContentBlock(block)` | — | 🆕 | **新增** — 估算单个内容块 token |
| `estimateToolResult(result)` | — | 🆕 | **新增** — 估算工具结果 token |

> **破坏性**：**无**。旧方法保留，新方法有默认实现。

### 2.2 新增 `TokenMeasurement` 类型

v0.1.5 引入了结构化的 token 测量结果：

```typescript
interface TokenMeasurement {
  /** 已消费的事件数量；等于下一个未读事件的 seq */
  readonly logRevision: SessionLogOffset
  /** 本次测量使用的基线锚点 */
  readonly baseline: TokenMeasurementBaseline
  /** 当前 surface 内容相对于基线的带符号 token 差值 */
  readonly surfaceDeltaTokens: number
  /** 当前请求+响应压力（非负值） */
  readonly totalTokens: number
  /** 当前 surface 的路由定价请求 token 总数 */
  readonly surfaceTokens: number
  /** 按位置顺序排列的当前 surface 节点 */
  readonly nodes: readonly TokenSurfaceNode[]
}
```

### 2.3 迁移路径

#### 场景 A：你只使用 `estimateMessage()`

**无需改动。** 该 API 在 v0.1.5 中保持不变。

```typescript
// 旧代码（v0.1.5 仍可用）
const tokens = ctx.tokenMeter.estimateMessage(message)
```

#### 场景 B：你需要更精细的 token 测量

**使用新增的 `measure()` API：**

```typescript
// v0.1.5 新写法 — 获取会话级精确 token 测量
const measurement = ctx.tokenMeter.measure(session)

// 使用测量结果
console.log('当前请求压力:', measurement.totalTokens)
console.log('Surface token 数:', measurement.surfaceTokens)
console.log('Surface 节点:', measurement.nodes)
```

#### 场景 C：你自定义了 token 定价策略

**使用 `TokenSurfaceNode` 替代简单的 token 计数：**

```typescript
// 旧写法（简化计数）
const totalTokens = nodes.reduce((sum, node) => sum + node.tokenCount, 0)

// 新写法（使用路由定价 + 启发式双精度）
const measurement = ctx.tokenMeter.measure(session)
for (const node of measurement.nodes) {
  console.log(`seq=${node.seq}`, `路由定价=${node.tokens}tok`, `启发式=${node.heuristicTokens}tok`)
}
```

### 2.4 对插件开发者的建议

- **计费插件**：如果插件需要向用户展示 token 消耗，推荐使用 `measure()` API，它提供路由感知的精确计费。
- **压缩插件**：如果插件需要判断是否触发压缩，使用 `measurement.totalTokens` 作为压力指标，比旧的启发式估算更准确。
- **缓存插件**：`measurement.surfaceTokens` 与 `measurement.surfaceDeltaTokens` 可以帮助判断 surface 是否发生了显著变化。

## 三、Permission Presets 统一服务

### 3.1 变更内容

v0.1.3 引入了 `dsh-permission-presets` 统一服务，v0.1.5 在此基础上进行了进一步加固。核心变化：

| 维度 | 旧方式（≤ 0.1.2） | 新方式（≥ 0.1.3 / 0.1.5 加固） |
|------|-------------------|--------------------------------|
| 沙箱控制 | `setSandboxMode(session, mode)` | `ctx.permissionPresets.set(session, presetName)` |
| 审批策略 | `setApprovalPolicy(session, policy)` | 同上，preset 内绑定了 sandbox + approval |
| 预设切换 | 分别设置两个 knob | 一次 `set()` 同时写入两个 knob |
| 当前状态查询 | 需要分别查询两个 knob | `ctx.permissionPresets.current(session)` 返回当前预设名 |

### 3.2 内置预设

| 预设名 | Sandbox | Approval | 说明 |
|--------|---------|----------|------|
| `workspace-write` | `workspace-write` | `ask` | 默认预设：可读写，需要审批 |
| `danger-full-access` | `danger-full-access` | `never` | 无限制模式：不需要审批 |

> `custom` 为保留字，表示"自定义组合状态"，不可作为预设名，也不是切换目标。

### 3.3 迁移路径

#### 场景 A：你直接调用了 `setSandboxMode()` 或 `setApprovalPolicy()`

**必须迁移到 `ctx.permissionPresets`：**

```typescript
// ❌ 旧写法（v0.1.3+ 不推荐）
setSandboxMode(session, 'workspace-write')
setApprovalPolicy(session, 'ask')

// ✅ 新写法（v0.1.3+）
ctx.permissionPresets.set(session, 'workspace-write')
```

#### 场景 B：你需要查询当前权限状态

**使用 `current()` API：**

```typescript
// ✅ 查询当前会话的预设
const currentPreset = ctx.permissionPresets.current(session)
// → 'workspace-write' | 'danger-full-access' | 'custom'

// ✅ 获取所有可用的预设选项
const presets = ctx.permissionPresets.names()
// → ['workspace-write', 'danger-full-access']

// ✅ 构建客户端选项
const option = ctx.permissionPresets.optionOf('workspace-write')
// → { value: 'workspace-write', name: 'Workspace Write', description: '...' }
```

#### 场景 C：你构建了自定义预设

**通过 `Config.presets` 扩展预设表：**

```typescript
// 在你的插件配置中扩展预设
interface MyPermissionConfig {
  presets?: Record<string, PresetSpec>
  defaultPreset?: string
}

// PresetSpec 类型
interface PresetSpec {
  sandbox: SandboxMode
  approval: ApprovalPolicy
  name?: string        // 显示名称
  description?: string // 用户说明
}
```

### 3.4 对插件开发者的建议

- **如果你的插件不涉及权限控制**：无需变更，保持现状。
- **如果你的插件需要动态调整权限**：使用 `ctx.permissionPresets.set()` 切换预设，不要直接操作底层 knob。
- **如果你的插件是 hook 插件（如 `permission-gate`）**：继续监听 `tools/pre-execute` 扩展点，权限预设不改变 hook 的行为模型。
- **`permission/preset` 事件**：预设切换会写入一个 log-only 事件 `permission/preset`，插件可以通过监听此事件做审计日志或状态同步。

## 四、Inbox 投影重构

### 4.1 变更内容

这是 v0.1.5 中**对插件影响最大**的变更之一：

| 维度 | v0.1.0-rc.5 ~ v0.1.4 | v0.1.5-rc.2 |
|------|----------------------|-------------|
| Inbox 服务 | `ctx.inbox` — 独立服务 | **不存在**，并入 agent-loop 内部投影 |
| 消息查询 | `ctx.inbox.getItems()` | 通过 `Agent` 接口的 `InboxState` 投影读取 |
| 消息入队 | `ctx.inbox.enqueue()` | 通过 `session` 对象追加事件驱动 |
| 事件类型 | InboxService 私有 | `agent/inbox/spliced` 等公开事件 |

> **破坏性**：**是**。如果你直接使用了 `ctx.inbox`，必须迁移。

### 4.2 新的公共接口

v0.1.5 不再暴露 `ctx.inbox`，而是通过以下接口提供 inbox 能力：

```typescript
// Agent 接口（核心入口）
interface Agent {
  readonly id: SessionId
  readonly inbox: InboxState  // 新的 inbox 访问方式
}

// InboxState 类型 — 插件编程的唯一表面
interface InboxState {
  /** 待处理消息的状态快照 */
  readonly items: readonly InboxItem[]
  /** 订阅 inbox 变化 */
  readonly onChange: (handler: () => void) => () => void
}

// InboxItem 类型
interface InboxItem {
  readonly id: string
  readonly text: string
  readonly source: 'user' | 'plugin' | 'system'
  readonly timestamp: number
}
```

### 4.3 迁移路径

#### 场景 A：你使用了 `ctx.inbox.getItems()`

**迁移到 `Agent.inbox` 投影：**

```typescript
// ❌ 旧写法
const items = ctx.inbox.getItems()

// ✅ 新写法 — 通过 Agent 接口访问
const agent = ctx.get('agent') as Agent
const items = agent.inbox.items

// ✅ 新写法 — 响应式订阅
const unsub = agent.inbox.onChange(() => {
  console.log('Inbox changed:', agent.inbox.items)
})
// 记得在 ctx.effect 中注册清理
ctx.effect(() => unsub)
```

#### 场景 B：你使用了 `ctx.inbox.enqueue()` 入队消息

**迁移到通过 session 事件追加：**

```typescript
// ❌ 旧写法
ctx.inbox.enqueue({ text: 'Hello', source: 'plugin' })

// ✅ 新写法 — 通过 session 事件
session.append({
  type: 'user/message',
  data: {
    content: [{ type: 'text', text: 'Hello' }],
    surfaceOp: { op: 'append' }
  }
})
```

#### 场景 C：你监听了 `inbox/change` 事件

**迁移到 agent-loop 投影：**

```typescript
// ❌ 旧写法
ctx.on('inbox/change', (event) => { ... })

// ✅ 新写法 — 监听 agent/inbox/spliced 事件
ctx.on('agent/inbox/spliced', (event) => {
  const { inserted, removed } = event.data
  // inserted 是新插入的消息
  // removed 是被处理的消息
})
```

### 4.4 对插件开发者的建议

- **UI 插件**：使用 `Agent.inbox.items` 渲染待处理消息列表，通过 `agent.inbox.onChange` 实现实时更新。
- **Hook 插件**：hook 插件无需修改 inbox 相关逻辑，继续监听 `tools/pre-execute` 等扩展点。
- **自动化插件（ACP/MCP）**：ACP 桥接器现在通过 `session.append()` 入队消息，不再依赖 `ctx.inbox`。

## 五、LLM Adapter 扩展

### 5.1 变更内容

`LlmAdapter` 从 3 方法扩展到 **7 方法**：

| 方法 | 0.1.0-rc.5 | 0.1.5-rc.2 | 说明 |
|------|-----------|-----------|------|
| `stream(options)` | ✅ | ✅ | 核心流式方法，保留 |
| `resolveModel()` | ✅ | ✅ | 保留 |
| `listModels()` | ✅ | ✅ | 保留 |
| `providerInfo()` | — | 🆕 | **新增** — 提供商品牌信息 |
| `providerRetryPolicy()` | — | 🆕 | **新增** — 提供商级重试策略 |
| `imageRequestPricing()` | — | 🆕 | **新增** — 图像请求计费信息 |
| `prepareCall()` | — | 🆕 | **新增** — 准备调用，HMR 安全隔离 |

> **破坏性**：**无**。新增方法都有默认实现，现有适配器无需立即实现。但如果你正在编写新的 LLM 适配器，建议全部实现以充分利用新功能。

### 5.2 新增方法详解

#### `providerInfo()` — 提供商品牌信息

```typescript
interface LlmProviderInfo {
  /** 提供商显示名称 */
  readonly displayName: string
  /** 提供商 URL */
  readonly url?: string
  /** 提供商图标标识 */
  readonly icon?: string
}

// 示例实现
providerInfo(provider: string): LlmProviderInfo {
  return {
    displayName: 'DeepSeek',
    url: 'https://deepseek.com',
    icon: 'deepseek-logo'
  }
}
```

#### `providerRetryPolicy()` — 提供商级重试策略

```typescript
// 示例：为不同提供商配置不同的重试策略
providerRetryPolicy(provider: string): ResolvedRetryPolicy | undefined {
  if (provider === 'openai') {
    return {
      mode: 'normal',
      maxRetries: 3,
      backoff: { type: 'exponential', initialDelayMs: 1000, maxDelayMs: 30000 }
    }
  }
  return undefined // 使用默认策略
}
```

#### `prepareCall()` — 准备调用（HMR 安全）

这是 v0.1.5 **最关键的新增方法**：

```typescript
// 将模型解析与流式分发绑定到同一适配器注册世代
// 防止 HMR（热模块替换）期间的错配
prepareCall(
  provider: string,
  model: string,
  signal?: AbortSignal
): Promise<PreparedAdapterCall>

// PreparedAdapterCall — 一次性调用的安全包装
interface PreparedAdapterCall {
  /** 已验证的适配器引用 */
  readonly adapter: LlmAdapter
  /** 已解析的模型配置 */
  readonly modelConfig: LlmResolvedModelInfo
  /** 一次性分发方法 */
  execute(signal: AbortSignal): AsyncIterable<StreamChunk>
}
```

**为什么需要 `prepareCall()`**：

在 HMR 期间，适配器实例可能被替换。如果直接调用 `stream()`，可能会使用到已被替换的适配器实例，导致请求分发到错误的版本。`prepareCall()` 确保模型解析和流式分发在同一注册世代内完成，提供原子性保证。

### 5.3 对 LLM 适配器开发者的建议

1. **实现 `providerInfo()`**：让 UI 层显示正确的提供商品牌名称和图标。
2. **实现 `providerRetryPolicy()`**：为不同提供商配置最优的重试策略，减少不必要的用户等待。
3. **迁移到 `prepareCall()`**：如果你的适配器支持 HMR，务必实现此方法以保障请求正确性。
4. **使用 `ReplayEnvelope` 替代 `unknown`**：v0.1.5 将 `replayState: unknown` 升级为结构化 `ReplayEnvelope`（`response` + `blocks`），提供更精确的重放元数据。

## 六、Sidebar Slot 变更

### 6.1 变更内容

v0.1.5 的 Sidebar 完全重写，引入了 **dockkit 停靠引擎** 和 **5 个固定 slot**：

| Slot Key | 类型 | 用途 |
|----------|------|------|
| `sidebar.brand.mark` | single | 品牌标志 |
| `sidebar.brand.name` | single | 品牌名称 |
| `sidebar.workspaces` | single | 工作区浏览器 |
| `sidebar.settings` | single | 设置入口 |
| `sidebar.footer.action` | list | 页脚操作（接收 `wide: boolean`） |

> **破坏性**：**对自定义 Sidebar 插件是**。旧的 Sidebar 插件可能需要重新适配 slot 契约。

### 6.2 关键约束

- 外壳只管理**几何**（折叠状态机、品牌行、New Session）
- 数据内容由填充 slot 的插件**自行管理**
- 可替换品牌但**无法替换导航控件**
- Props 只有 `wide: boolean` + `expandSidebar()` 穿过外壳边界
- **消息轨（TurnNavigator）硬编码在 ChatView 中，无 slot 暴露**

### 6.3 迁移路径

#### 场景 A：你的插件贡献了 Sidebar 内容

**适配新的 slot 契约：**

```typescript
// ✅ 新写法 — 注册到 sidebar.footer.action（list 类型 slot）
ctx.slots.inject('sidebar.footer.action', () =>
  ctx.slots.register(
    {
      name: 'sidebar.footer.action',
      key: 'myplugin-action',
      order: 100,
    },
    MySidebarFooterAction,
  ),
)

// ✅ 接收 wide 参数
function MySidebarFooterAction({ wide }: { wide: boolean }) {
  return wide ? <FullWidthAction /> : <CompactAction />
}
```

#### 场景 B：你的插件使用了旧版 Sidebar API

**检查兼容性：**

```typescript
// 检测 Sidebar 重写是否影响你的插件
const sidebarSlot = 'sidebar.footer.action'
if (ctx.slots.get(sidebarSlot)) {
  // v0.1.5+ — 新的 slot 系统
} else {
  // v0.1.0-rc.5 ~ v0.1.4 — 旧的 Sidebar 系统
}
```

### 6.4 对插件开发者的建议

- **不要直接操作 DOM 定位 Sidebar**：v0.1.5 的 Sidebar DOM 结构完全改变，旧的 DOM 锚点选择器会失效。
- **使用 slot 系统**：所有 Sidebar 内容应通过 slot 注册，而非直接渲染。
- **评估 dockkit 冲突**：如果你的插件使用了自定义停靠/拖拽功能，需要检查是否与 dockkit 引擎冲突。

## 七、Session V3 格式升级

### 7.1 变更内容

| 维度 | V2 (0.1.2/0.1.3) | V3 (0.1.5) |
|------|------------------|-----------|
| 系统提示词 | 普通消息 | `surface node zero` |
| 格式 | projection-based | surface node + surface op |
| 持久化 | handle-based | V3 writer |
| 压缩方式 | shadowed range | surface node 替换 |

> **破坏性**：**对直接读取 session 数据的插件是**。内置 V2→V3 迁移管线会自动迁移旧 session，但插件如直接读取 session 数据需手动适配。

### 7.2 迁移路径

#### 场景 A：你的插件通过 API 读取 session（推荐）

**无需改动。** 所有 session 数据通过 `ctx.session` 和 `ctx.tokenMeter` 等抽象接口访问，不直接解析日志。

```typescript
// ✅ 推荐方式 — 通过抽象接口
const agent = ctx.get('agent') as Agent
const measurement = ctx.tokenMeter.measure(agent.session)
```

#### 场景 B：你的插件直接读取 JSONL 日志

**需要适配 V3 格式：**

```typescript
// ❌ 旧写法 — 假设系统提示词是普通消息
function extractSystemPrompt(events: SessionEvent[]) {
  const first = events.find(e => e.type === 'user/message')
  return first?.data?.content ?? ''
}

// ✅ 新写法 — 识别 surface node zero
function extractSystemPromptV3(events: SessionEvent[]) {
  const zeroNode = events.find(e =>
    e.type === 'user/message' &&
    e.data.surfaceOp?.op === 'zero' // surface node zero
  )
  return zeroNode?.data?.content ?? ''
}
```

## 八、子代理目录与模型路由

### 8.1 变更内容

v0.1.5 为子代理系统新增了两大能力：

1. **子代理目录**：父代理可以持久化、枚举所有子代理（one-shot / continuable）
2. **子代理模型路由**：每个子代理可独立指定 provider / model / reasoningEffort

### 8.2 新增类型

```typescript
// 子代理目录入口
interface SubagentCatalogEntry {
  childId: string
  mode: 'one-shot' | 'continuable'
  label?: string
  status: 'running' | 'idle' | 'ready' | 'terminal'
}

// 子代理模型路由选项
interface AgentOptions {
  provider?: string
  model?: string
  reasoningEffort?: ReasoningEffortId
  maxTokens?: number
}
```

### 8.3 对插件开发者的建议

- **工作流插件**：可以使用 `maxTotalAgents` 控制每个 workflow 的最大子代理数。
- **监控插件**：通过 `listChildren()` / `listDescendants()` 枚举子代理状态。
- **模型选择插件**：可以在 `AgentOptions` 中为不同子代理指定不同的模型。

## 九、迁移检查清单

按照以下顺序逐项检查：

### 必须做

- [ ] **Session 数据读取**：如果插件直接读取 session JSONL 数据，适配 V3 surface node 格式
- [ ] **Inbox 服务**：如果使用 `ctx.inbox`，改为通过 `Agent.inbox` 投影访问
- [ ] **权限控制**：如果直接调用 `setSandboxMode` / `setApprovalPolicy`，改为 `ctx.permissionPresets.set()`
- [ ] **Sidebar 插件**：检查是否与新的 dockkit 停靠引擎冲突，适配 slot 契约
- [ ] **系统提示词**：如果依赖系统提示词消息语义，适配 surface node zero

### 建议做

- [ ] **Token 计量**：使用 `ctx.tokenMeter.measure()` 替代启发式估算，获取更精确的计费
- [ ] **LLM Adapter**：如果编写新适配器，实现 `providerInfo()`、`prepareCall()` 等新方法
- [ ] **Sidebar Slot**：使用新的 5 个 slot 注册系统，不使用旧的 DOM 锚点
- [ ] **子代理监控**：使用 `listChildren()` 枚举子代理状态，替代旧的查询方式
- [ ] **评估 Electron 桌面打包**：检查桌面打包对插件的影响

### 不需要做

- [ ] ~~`LlmAdapter` 新增 4 方法~~ — 有默认实现，不强制
- [ ] ~~`@Remote` 装饰器~~ — 全新机制，不影响现有代码
- [ ] ~~`TypertRegistryContract`~~ — 全新运行时注册表

1. 在 DSH v0.1.5-alpha.1 上测试插件加载
2. 在 DSH v0.1.5-rc.1 上测试插件功能
