## 1. 设置席位 API（TODO）

### 变了什么

| 项 | 0.1.6-alpha.1 | 0.1.7-rc.1 |
|---|---|---|
| 注册 API | `settings.installSection(owner, ns, schema, entry, hooks)` | **`settings.configure(presentation, owner)`** |
| 代码库引用数 | 15 个文件 | **0 个文件**（无垫片） |
| 命名空间 | `SettingsNamespace` 字符串 | **无此概念** |
| 权威存储 | `$DSH_HOME/settings.yaml` | 活动 profile 的 `cordis.patch.yml` |

复核（预期输出 `15 / 15 / 0`）：

```powershell
foreach ($t in @('dsh-v0.1.5-rc.2','dsh-v0.1.6-alpha.1','dsh-v0.1.7-rc.1')) {
  "$t : " + (git -C <repo> grep -c 'installSection' $t -- packages | Measure-Object).Count
}
```

### 新 API

服务方法签名（`packages/settings/settings/src/index.ts:266`）：

```ts
configure(presentation: { auto?: boolean }, owner: Fiber = this.ctx.fiber): () => void
```

- 返回 disposer；
- **同一 fiber 重复配置直接抛错**：`Settings presentation is already configured for this plugin instance`（同文件 `:268`）。

官方 README 原文：

> A plugin that ships its own page registers `configure({ auto: false }, ctx.fiber)` as an effect inside an optional `ctx.inject(['settings'], ...)` child from `apply`: the child names the plugin fiber the policy belongs to, a late-loading or replaced Settings service picks the policy up, and the business plugin runs without Settings. The policy does not remove configuration reads or writes.

### 改法

**删掉**旧的（0.1.6 形态）：

```ts
// ❌ 0.1.7 上不存在
settingsCtx.settings.installSection(ctx, MY_NS, MySettingsSchema, entry, { … })
```

**改成**（官方各包一致采用的模式，例如 `packages/client/ui-theme/src/index.ts:40`、`packages/core/agent-default-model/src/index.ts:58`）：

```ts
// ✅ 自带设置页的插件
export function apply(ctx: Context) {
  // …业务逻辑：直接读自己的 Config…

  ctx.inject(['settings'], (child) => {
    child.effect(() => child.settings.configure({ auto: false }, ctx.fiber))
  })
}
```

三个关键点，缺一个就会踩坑：

1. **必须放在 `apply` 内的 `ctx.inject(['settings'], …)` 子上下文里**——该子上下文**命名了策略所属的插件 fiber**。这样晚加载或被替换的 Settings 服务能拾取该策略，而**没有 Settings 时业务插件照常运行**（这是它相对旧 API 的主要收益）。
2. **必须是 effect**（`child.effect(...)`）——销毁时自动回卷。
3. **不要为此把 `settings` 写进顶层声明式 `inject`**——那会让插件在无 Settings 的 profile（如部分 headless 组合）里挂起。

### 如果你的插件原本注册的是 `settings.plugin.item`

**该席位在 0.1.7 已被移除**，需要换席位。

实测席位存活情况：

| 席位 | 0.1.5-rc.2 | 0.1.6-alpha.1 | 0.1.7-rc.1 |
|---|---|---|---|
| `settings.plugin.item` | 13 | 13 | **1（仅剩一处历史注释）** → **已移除** |
| `settings.plugins.tab` | 9 | 9 | **8** → 仍在 |
| `settings.section` | 21 | 21 | **21** → 仍在 |
| `settings.onboarding` | 14 | 14 | 14 → 仍在 |
| `settings.models.provider-card` | 8 | 8 | 8 → 仍在 |
| `settings.models.sign-in` / `settings.models.footer` | 有 | 有 | 有 |

0.1.7 声明席位的权威位置是 `packages/client/ui-settings/src/client/contract/slots.ts`：

```ts
'settings.section': { kind: 'list'; scope: 'root'; owner: SettingsSectionOwnerProps }      // :57
'settings.plugins.tab': { kind: 'list'; scope: 'root'; owner: SettingsPluginsTabOwnerProps } // :66
```

`packages/client/ui-settings/README.md` 的分工原文：

> The shell (`sidebar.settings` occupant, navigation, chrome) lives in ui-settings-general; **feature pages register `settings.section` contributions**; the **Plugins section hosts `settings.plugins.tab` pages**; onboarding steps register `settings.onboarding`.

**迁移映射建议**：

| 你原来的席位 | 建议去处 |
|---|---|
| `settings.plugin.item`（小型配置卡片，进"配置"列表） | 首选：**不再注册席位**——把字段标为 `.volatile()`（见 §2），让宿主 schema 派生的表单承载 |
| `settings.plugin.item`（需要自定义布局） | 次选：`settings.plugins.tab`（独立 tab 页） |
| `settings.plugins.tab` / `settings.section` | **无需改动**（席位仍在） |

### 客户端读写配置的新 API

`ctx.configForms` 是 0.1.7 **全新**的客户端 API（实测 0 → 0 → **67** 个文件引用）：

```ts
// packages/client/ui-settings/README.md
// Feature adapters use `ctx.configForms.get(entryId)` to obtain accepted values and a write queue
// shared by every editor of that Host entry.
const forms = ctx.configForms.get(entryId)
// 快照含：resolved `value`、inherited `base`、raw `user`、revision、writability、persistence mode
// 写入：set / unset（单次操作）、mutate（一次原子操作列表）
// 跨命名空间：ctx.configForms.describe()
```

要点：编辑提交时**带上编辑前读到的 revision**；冲突会保留草稿。**取消覆盖**（`unset`）恢复继承值。

## 2. 设置可热改字段（TODO）

### 变了什么

**`.volatile()` 是 0.1.7 全新机制**——在 0.1.6-alpha.1 中**完全不存在**（实测 `git grep -c '\.volatile(' ... -- packages` 命中 0 个文件）。

> Settings 的表单**只暴露 `.volatile()` 字段**。未声明的普通配置字段**不会**出现在设置页，只能通过 Cordis 配置文件编辑。

### 改法

在插件的 Config 接口上，把需要热改的字段包成 `Volatile<T>`：

```ts
import type { Volatile } from '@deepseek-ai/cordis'
import z from '@deepseek-ai/schemastery'

export interface Config {
  /** 凭证引用（环境变量名），按请求解析；默认 DEEPSEEK_API_KEY。 */
  apiKeyEnv: Volatile<string>
  /** 端点 base；回退到可信环境层的 $DEEPSEEK_BASE_URL，再到公共 API。 */
  baseURL: Volatile<string | undefined>
  /** 部署思考策略；disabled 把每个会话请求限制为 off。 */
  thinking: Volatile<'enabled' | 'disabled' | undefined>
  /** 默认思考强度（默认 high）；off 按请求禁用 thinking。 */
  reasoningEffort: Volatile<'off' | 'low' | 'high' | 'max' | undefined>
  /** 默认单请求输出上限（默认 256,000）；模型自身上限与显式请求值优先。 */
  maxTokens: Volatile<number>
}
```

（以上字段与注释取自 `packages/llm/llm-deepseek/src/config.ts`，为官方真实写法。）

### 消费侧：按操作读取引用

note 原文要求："Fields that can change without remounting use `.volatile()`; **consumers read their references during operations**."

即**不要**在 `apply` 时把 volatile 字段的值快照到长期闭包里——应在每次操作时读取。判定字段是否为 volatile 可用 `isVolatile`（来自 `@deepseek-ai/cosmokit`）。

### ⚠️ 已知覆盖语义（官方明确记录的限制）

Cordis 的 config patch **替换整条 entry 的 config**。因此当用户通过设置表单编辑你的插件时，**整条 entry 的完整 config 会被写进 profile 行**：

> Other edits store the entry's complete config in the profile row: the ordinary fields as composed at write time plus every volatile field. Later bundle changes to those fields do not reach that profile until the entry's config override is removed.

官方在 shipped bundles 里列出的四个会被"钉住"的真实字段（可作为你的自查参照）：

| entry | 被钉住的字段 | 触发场景 |
|---|---|---|
| `permission` | `presets` | 改过默认预设之后 |
| `agent-presets` | — | 选过预设之后 |
| `agent-loop` | `agents` | 改过并行度之后 |
| `web-search-deepseek` | `apiKeyEnv` | 改过 Web Search 之后 |

并且：**客户端会把该行的每一个 volatile 字段都标记为"已覆盖"，而不只是被编辑的那个**。

官方把它定义为当前限制而非缺陷："Narrowing a write to the edited fields needs merge semantics for patch `config`, which Include does not provide."

**对你的含义**：如果你的插件后续版本改了某个 volatile 字段的默认值，**已编辑过的用户不会自动拿到新默认值**——他们需要 reset 该 entry（移除 config 覆盖）才会重新继承。

## 3. `@deepseek-ai/dsh*` peer 范围强制校验（TODO）

### 变了什么

`apps/cli/README.md` 新增：

> Installation and profile startup enforce declared DSH peer ranges against the same runtime version shown by `dsh --version`. Incompatible plugins require an explicitly acknowledged exact-version exemption.

**⚠️ 最容易读错的一点**：这里的 "DSH peer ranges" 是 **`peerDependencies` 里 `@deepseek-ai/dsh` / `@deepseek-ai/dsh-*` 的范围**，**不是 `engines.dsh`**。

源码铁证（`packages/boot/app-boot/src/plugin-compatibility.ts` 的 `evaluatePluginCompatibility`）：

| 行 | 事实 |
|---|---|
| `:68` | **无 `peerDependencies` 字段 → 直接判定兼容并返回**，根本不看 `engines` |
| `:69` | 只解析 `peerDependencies` |
| `:75` | 只取 `@deepseek-ai/dsh` / `@deepseek-ai/dsh-*`，其余 peer 跳过 |
| `:76` | `workspace:^` / `:~` / `:*` 视为**当前运行时版本** |
| `:77` | `semver.satisfies(runtime, requirement, { includePrerelease: true })` |
| `:84-87` | 豁免键 `name@version` → **精确运行时版本数组**（双钉） |
| 全文 | **`engines.dsh` 未被读取** |

官方文档原文直证：

- `packages/boot/app-boot/README.md:52`：`Before a profile imports a plugin, DSH checks its \`peerDependencies\` on \`@deepseek-ai/dsh\` and \`@deepseek-ai/dsh-*\`…`
- `packages/util/package-manifest/README.md:93`：`**Compatibility is declarative.** Current installers and loaders do not enforce \`dsh.manifestVersion\` or \`engines.dsh\`…`

拒绝错误形态：

- 错误码 **`incompatible-version`**；
- 逐包返回 `name`、`version`、`runtimeVersion`、未满足的 `peers`；
- **CLI 拒绝会打印确切的 `allow-version` 命令**；Web 页面用自己的 locale 字典措辞。

### 改法

**把兼容性约束写在 `peerDependencies`**，而不是 `engines`：

```json
{
  "peerDependencies": {
    "@deepseek-ai/cordis": ">=0.1.5-rc.2 <0.2.0"
  },
  "devDependencies": {
    "@deepseek-ai/cordis": ">=0.1.5-rc.2 <0.2.0"
  },
  "engines": {
    "node": ">=24"
  }
}
```

三点注意：

1. **与宿主共享单例的包必须 `peerDependencies` + `devDependencies` 双写**（官方 `docs/user/develop/basic/publish.md` 区间新增的规则）。典型需要双写的：`@deepseek-ai/cordis`、`dsh-scope`、`dsh-mcp-client` 等跨包共享身份的包。
2. **`engines.dsh` 仍可写但无准入效果**——它是市场/文档信号。若你想让它在未来生效，先确认官方已引入对应 reader。
3. 该校验路径用 `includePrerelease: true`，所以 `>=0.1.5-rc.2 <0.2.0` **能**匹配 `0.1.7-rc.1`。但 pnpm 自身的 peer 解析未必同样宽松，`-0` 上界技巧仍有适用面（[distribution-strategy.md §六](distribution-strategy.md)）。

需要强制安装时的豁免命令：

```sh
dsh plugin --profile <profile> version-exemptions
dsh plugin --profile <profile> allow-version <package@version> --dsh-version <runtime> --accept-risk
dsh plugin --profile <profile> revoke-version <package@version> --dsh-version <runtime>
```

`allow-version` 是**精确版本**豁免（不是范围豁免），授予前会打印风险警告。

## 4. `settings.yaml` 移除（TODO）

### 变了什么

全局 `$DSH_HOME/settings.yaml` 已移除；设置权威改为**活动 profile 的 `cordis.patch.yml`**。

旧文件的一次性导入规则（`packages/settings/settings/README.md` 与 note 一致）：

- 时机：Settings 启动后、**Loader 已 settle 每个 entry** 时执行一次；
- 映射：section id 即 entry id，另有三条固定映射——`ui-developer-tools` → `ui-settings`、`ui-onboarding` → `ui-settings-general`、`shell` → 该平台的 shell executor entry；
- 落定：文件在**首次写入前**改名为 `settings.yaml.imported`，所以导入**永不重复**；
- 被拒绝的 section：记日志，且**只留在改名后的文件里**。

端到端证据：`apps/web/tests/settings-import.e2e.ts`（断言原文件消失、`.imported` 内含导入值）。

### 改法

| 你的做法 | 改成 |
|---|---|
| 部署脚本写 `$DSH_HOME/settings.yaml` | 写目标 profile 的 `cordis.patch.yml`（按 entry id 定位行） |
| 期望设置在多个 profile 间共享 | **不再可能**。note 明确持久化的表单值是 profile 专用的；要共享偏好必须引入**显式的共享 Cordis 层**并定义写目标 |
| 自动化断言 `settings.yaml` 存在 | 删除该断言（它会被改名） |

## 5. `patchReload` 移除（TODO）

### 变了什么

```ts
// 0.1.6-alpha.1
export interface DshProfileManifest {
```

## 7. 会话格式 V4（TODO）

### 变了什么

| 项 | 0.1.6-alpha.1 | 0.1.7-rc.1 |
|---|---|---|
| `SESSION_FORMAT_VERSION` | 3 | **4** |
| 迁移包 | …v2→v3 | **+ `packages/session/session-format-v3-to-v4/`** |
| 工具结果 | content-block 联合中的 `tool-result` | **tool-role 消息**（必需 `toolCallId`，可选 `isError`） |
| source 归因 | 已发布插件包装器 | **生产者自有 source** |
| `turn/end.reason` | — | **新增 `forked`** |
| 新事件 | — | **`developer/message`**（无 shipped profile 发出） |

**关键运营事实**：`docs/session-format-status.md` 显示 writer 已是 **4**，但 `latestReleasedVersion` 仍是 **3**（evidenceTag `dsh-v0.1.5-alpha.1`）。官方强调 alpha/beta/rc 级发布**即已建立已发布会话格式义务**，prerelease 标记**不会**让持久化数据变得可丢弃。

**不可回退**：V3 reader 拒绝更新的代际；官方不支持降级。

### 文件后果

- **读 open** 在内存中准备迁移结果，**不发布**后继；
- **写 open** 把当前版本命名的后继**独占发布**在未改动的前代文件旁；
- 结果：会话目录出现 `session.v4.jsonl[.zstd]`，前代文件保留且不再写入；
- 命名规则：v0 用 `session.jsonl[.zstd]`，**v1 及之后用 `session.vN.jsonl[.zstd]`**；已提交代际路径**永不重命名/替换/删除**。

### 改法（插件侧）

| 你的插件 | 改法 |
|---|---|
| 直接读 `session.jsonl` | **停止**该假设；改用 `SessionPersistence`（`create`/`open`/`stat`/`list`/`export`）或 `ctx.sessions` |
| 解析 content-block 并处理 `tool-result` | `tool-result` 已退出该联合；改按 tool-role 消息处理，携带 `toolCallId` / `isError`（**代码级改法见 §11.2**） |
| 依赖已发布的插件 source 包装器 | 改按生产者自有 source；PTC 生产者为 `source.kind: 'ptc-mode'`（历史 `tools-code-mode` / `tools-ptc` 仍被映射） |
| 处理 `turn/end` | 处理新增的 `reason: 'forked'` |
| 依赖 `request/header` 的 `system` 键 | 该键已**记为禁止**；不要写它 |

> 排查提示：如果你在 0.1.5/0.1.6 上写过"自定义 message source kind"，请先读 [upgrade-pitfalls.md §1.1](upgrade-pitfalls.md)——那类做法在旧版就会导致会话永久拒载，在 V4 上后果更重。

## 8. 多语言显示元数据（新能力）

插件可以在自己的 `locale/<language>.json` 里提供 `meta.title` / `meta.description`，让**插件管理页与设置页的插件清单**显示可读标题与简介（**包括被禁用的插件**）：

```json
{
  "meta": {
    "title": "File Search",
    "description": "Search files in your workspace."
  }
}
```

必须同时声明资源导出：

```json
{
  "exports": {
    "./locale/*.json": "./locale/*.json"
  }
}
```

| 主题 | 契约 |
|---|---|
| 地址来源 | 由**配置里的 Cordis 插件名**决定；不评估插件代码 |
| 纯 JS 路径插件 | `./plugins/search.js` 这类**不做同级查找**，配置路径本身即最终标题回退 |
| 语言发现 | Host 解析 `en.json` 并在同目录发现其它语言；语言标识大小写不敏感，**重复被拒** |
| title 回退 | `meta.title` → 同级 `package.json` 的非空 `name` → 完整配置插件名 |
| description 回退 | `meta.description` → 同级 `package.json` 的非空 `description` → 无描述 |
| 子路径插件 | **不继承**所属包的介绍 |
| 错误语义 | 缺资源/缺字段走回退；**非法字段或畸形文件报诊断而非静默回退**，插件仍可管理 |
| 缓存 | **按请求读取，无缓存** |

**发布注意**：漏掉语言文件或漏声明导出，会让**发布后**元数据不可用——验证要同时覆盖**解析**与**打包进包的文件**。

详见 [i18n-multilingual-guide.md](i18n-multilingual-guide.md)。

## 9. 补丁层支持有序文件列表

`dsh.bundle.patch` 从 `string` 变为 `string | string[]`（提交 `654caa4bbd`，PR #4722）：

```json
{
  "dsh": {
    "bundle": {
      "patch": ["./base.patch.yml", "./web.patch.yml"]
    }
  }
}
```

语义：启动器按序把它们作为**一个层**应用，**每个文件的相对插件路径在该文件旁解析**。

`string` 形式仍然合法，**无需强制迁移**。

## 11. rc.1 → rc.2 补遗（实机迁移实证，2026-09-26）

> 本文主体基于 rc.1 对比。以下各项在 `dsh-v0.1.7-rc.2` 实机迁移中实测（4 个自有插件：
> context-compression-improved / thinking-levels / session-guard / prime-memory），rc.1 上通过的代码在 rc.2 会挂。

### 11.1 `SettingsScope` 导出移除 + configForms 上下文合并冲突

| 项 | rc.1 | rc.2 |
|---|---|---|
| `SettingsScope` / `SettingsScopeSnapshot` | 从 `@deepseek-ai/dsh-client-ui-settings/client` 导出 | **不再导出** |
| `Context.configForms` 合并 | 需插件自己 `declare module` | **宿主包已合并**（`ConfigForms` 类），插件再声明会 TS2717 冲突 |

改法：删掉本地 `configForms` 的 `declare module` 合并；`SettingsScope` 换成**本地结构化镜像**（`getSnapshot/subscribe/set/unset(/mutate)` 五个成员，形状见 [settings-seat-017-recipes.md §3.5](settings-seat-017-recipes.md)），卡片照常用 `configForms.get(entryId)` 的返回值赋给它（结构兼容）。

### 11.2 tool-result 消息化的"改哪几行"（§7 的代码级补充）

§7 讲了 V4 会话格式，这里是从 0.1.5 代码迁到 rc.2 时实际要动的位置：

```ts
// ❌ 旧：结果块是 content[0]
const result = event.data.message.content[0]      // ContentBlock
result.content / result.isError
event.data.message.source.callId

// ✅ rc.2：tool 结果就是 tool-role 消息本身
const message = event.data.message as ToolResultMessage
message.content / message.isError
message.toolCallId
```

排查清单：

- 全仓搜 `content[0]`（host 半的解包点，rc.2 上全是类型错误，一个不漏）；
- 全仓搜 `'tool-result'`——它已**退出 `ContentBlockMap`**（现为 text/reasoning/image/file/tool-call/tool-addition/tool-removal），遍历分支直接删；
- 压缩/裁剪类的"结果替换"从"替换包裹块"改为直接替换 `message.content`。

### 11.3 message source kind 自有化

共享 `source.kind: 'plugin'`（`{ kind: 'plugin', plugin: '…' }`）**已删**，`MessageSourceMap` 是 merge-extensible 总和，每个生产者声明自己的 kind（官方样板：compaction 的 `'compact-checkpoint'`，`packages/compaction/compaction/src/index.ts:26`）：

```ts
declare module '@deepseek-ai/dsh-llm' {
  interface MessageSourceMap {
    'my-plugin': { readonly kind: 'my-plugin' }
  }
}
// 写入：createUserMessage({ content, source: { kind: 'my-plugin' } })
// 校验：replacement.data.source.kind !== 'my-plugin'
```

### 11.4 primitives 图标改名

`IconChevronDownOutline14` → **`IconChevronDownOutlineMedium`**。rc.1 名字在 rc.2 上是 `undefined` 导入——**type 过不了是幸运**；若构建时 tree-shake 掉引用（bundle 里无该符号），远端运行时才在渲染期炸 `Element type is invalid`。**测试桩同步改**（`tests/support/ui-primitives.tsx` 一类 mock 里的旧名会让客户端测试假失败）。

### 11.5 包装 observable 必须缓存 getSnapshot（React #185）

旧 `settingsScope.bind()` 返回的 scope 由宿主缓存快照，业务代码从未关心引用稳定性；rc.2 迁移中自建的适配层（`configForms.get(entryId)` → 旧 scope 形状）若每次 `getSnapshot()` 都构造新对象，`useSyncExternalStore` 会无限重渲染，生产环境表现为 `Minified React error #185` + `slot entry crashed in '<席位>'`（错误边界撤下整个 entry）。**契约**：observable 的 getSnapshot 必须返回身份稳定的引用，直到源变化；以源快照对象身份为缓存键重算投影，并加 `getSnapshot() === getSnapshot()` 回归断言（mock 快照天然稳定，测不出此 bug）。

### 11.6 版本线同步：workspace overrides / devDeps 没升级的"分裂"症状

compat 分支只改了业务代码、没动构建环境时，会出现：

| 症状 | 根因 |
|---|---|
| 本地 typecheck 满屏红（`volatile` 不存在、类型成员缺失），远端运行正常 | `pnpm-workspace.yaml` 的 `overrides` 还钉着旧宿主（0.1.5-rc.2 + schemastery 3.18.2）。发布包不带 overrides，消费者拿到 package.json 声明的新版本，所以远端没事 |
| typecheck 报 `Cannot find module '@deepseek-ai/dsh-client-store'` 等**间接**类型缺失 | rc.2 宿主包的 .d.ts 类型链引用了新传递依赖；devDeps 需补（同轮还补了 `@deepseek-ai/cosmokit`） |
| devDeps 直接钉版本号（无 overrides 的仓） | 逐个 bump 到 `0.1.7-rc.2` |

**改法**：compat 分支开工第一件事就把 `pnpm-workspace.yaml` overrides（宿主包 → `0.1.7-rc.2`，schemastery → `3.18.4`——**3.18.2 没有 `.volatile()`**；个别包没有 rc.2 就钉可用的最高版本）与 devDeps 同步升级，再做业务迁移——否则类型错误会把真实迁移点淹没。

> 附带纪律：升级 overrides 后先跑 `pnpm run typecheck` 拿到**干净基线**，再动手迁移；迁移完跑一次测试并与迁移前基线对比（`git stash → test → stash pop`），分清"本来就红"和"改红了"。
