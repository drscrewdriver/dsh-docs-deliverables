## 1. 全景：六个控制面

| # | 控制面 | 解决的问题 | 主要落点（案例） | 一句话口径 |
|---|---|---|---|---|
| **F1** | 分批 / 分块 | 单次调用太大 → 超时、prompt 爆炸、失败半径过大 | L1 抽取分块、去重批、L2 场景分块、reindex 批、sqlite `IN_CHUNK`、图谱 `chunkOf` | **按字符/条数切块，失败半径 ≤ 一块** |
| **F2** | 子进程拆分 | 同进程 DLL 撞名；ORT 同步调用冻结宿主；崩了拖死宿主 | `resources/embedding-child.cjs` + `store/local-embedding.ts`、worker 逃生门 | **原生重活一律出进程** |
| **F3** | 崩溃自愈 | 崩一次停摆到宿主重启 | `respawnChannel()` / `crashCb` / `ack` 断点续试 | **有界重启：60s ≤2 次 + 只续一次** |
| **F4** | 压力控制 | 慢依赖拖垮写入；反复撞同一堵墙 | `EmbedHelper` 断路器、抽取退避、`dedupRetryCap`、`consecutiveFailCap`、LLM 回退链、召回/输出预算 | **快失败 + 降级 + 有界重试** |
| **F5** | 队列与优先级 | 后台填充堵塞用户请求 | 管线任务队列 `pickNextTaskIndex`、graph 泵护栏、子进程推理队列 `priority` | **live 永远优先，批可以被插队** |
| **F6** | 预算留痕与观测 | 规模越界后无法追责/复现 | `tokensMax` / `pid` / `execPath` / `embedding_meta` / receipt digest / trace | **每个越界都要留可核对的数** |

> **F1 决定「一次处理多少」，F2 决定「在哪处理」，F3 决定「坏了怎么活」，F4 决定「慢了怎么退」，F5 决定「谁先跑」，F6 决定「事后能不能证明」。**

**F1 的不变量**（案例原文）：任何「一次处理 N 条」的地方都必须有 N 的上界与「失败只影响本块」的语义；没有上界的批是债，不是性能。

## 2. 各面关键机制（节选）

### F1 分批 / 分块

| 落点 | 机制 | 处理记录 |
|---|---|---|
| L1 抽取分块 | `perChunk = min(上限, max(下界, llm.maxInputChars − 余量))`，再受模型容量与「该路由学到的块长」二次收紧 | 每块 try/catch + 失败块留 pending（部分消费，不整批丢）；整轮墙钟预算；**学到的块长只降不升** |
| L1 去重分批 | 按固定条数切块发 LLM | 教训：旧版整批丢单次调用，prompt 随候选池线性膨胀 → 改为**批内预收拢**，而**不是**加大批 |
| L2 场景整合 | 复用同一分块函数，单块路径与旧逻辑逐字一致（零漂移） | 旧版整族 backlog 单调用实测 >60s abort；分块后失败半径从「整族」缩到「一块」 |
| reindex（补向量） | 按固定条数取记录批量嵌入 | 崩后由它逐批补齐；`undefined` 空洞按「本轮未取到」跳过（不炸整轮） |
| 重建调用估算 | `estimateCalls()` | 让用户在触发重建前看到「大概多少次调用」，而不是跑完才知道 |
| sqlite 批量 | IN 列表分块（避开变量数上限）+ skip 集封顶 | 封顶后宁可漏记也不爆内存 |

### F3 崩溃自愈

| 机制 | 值 / 行为 | 为什么这样 |
|---|---|---|
| 单点发起 | 只有 `crashCb` 能触发重启；`respawnPromise` 合流 | 否则 warmup / embed / reindex 三个入口会并发 fork（风暴） |
| 速率窗 | 60s 内 ≤2 次 | fork+ready + 首条 ≈ 2.9s/次；反复 fork 比停摆更贵 |
| 断点续试 | 逐条上报进度，崩后 `texts.slice(ack)` **只续一次** | 不整批重放（毒输入会活锁）；头段向量随之丢失 → 交周期性 backfill 补 |
| 终态钉死 | `close()`/`terminated` 后任何 exit/crash 都不复活 | 否则卸载/切源后残留重嵌循环会把模型重新加载常驻 |
| 超限终局 | 超过速率窗 → 回 failed | 有界失败优于无限重启 |

**表述红线**（案例原文）：自愈**不保证不丢向量**（头段空洞 = 少一批）；也不宣称消除崩溃。

### F4 压力控制

| 机制 | 参数形态 | 行为 | 为什么 |
|---|---|---|---|
| 慢调用断路器 | 慢阈值 / 冷却窗 / EMA / 连续失败阈值 | 熔断期内直接返回 `undefined` → 调用方降级为纯文本检索；冷却后半开探测一次 | 不让每条写入都干等一次慢嵌入；所有调用方本就有 `undefined` 降级路 |
| 抽取退避 | per-session `nextAt` | 退避窗内跳过该会话 | 一个坏会话不应反复烧 LLM |
| 连续失败上限 | 去重 / L2 各有一个 cap | 达上限 → fail-loud + park | 失败要显性停，不要默默循环 |
| 分层输出预算 | 每层一个 maxTokens（抽取 < L2，去重最小） | 每层调用带显式 maxTokens | 层与层信息密度不同；用小预算压长尾成本 |
| LLM 回退链 | 主路由失败按序降级 | 每条路由**各享全额**超时 | 慢首包模型的回退位要留足时间 |
| 召回预算 | 条数 / 单条字符 / 总字符 / 超时 | 超时**静默跳过本轮** | 绝不因为召回慢而拖慢对话 |

### F5 队列与优先级

| 队列 | 选择规则 | 关键护栏 |
|---|---|---|
| 管线任务队列 | **live > graph > 队首** | `drain()` 单飞（不并发跑任务）；单任务失败只 warn，不中断后续 |
| 图谱泵 | 单飞；每轮至多消费 1 个任务 | 永远让位 live；claim 落空即停泵（不空转） |
| 子进程推理队列 | 单条且高优先级 → 插队；批 → 队尾；条与条之间让路 | 用户 query 插到长批之前，批内条目仍可被后来者插队 |

> F5 的本质不是「吞吐优化」，而是**优先级与饥饿控制**——后台工作永远不能把用户轮次卡住。

### F6 留痕

| 留痕 | 回答什么 |
|---|---|
| 每批最大 token 数（`-1` = 不可证） | 这一批真正进模型多少 |
| `pid` / `execPath` / `release` | 崩的是哪个子进程、跑在哪种运行时下 |
| 生效 token 预算 | 库里的向量是在哪个帽下嵌出来的（只记录，不进重嵌判据） |
| 去重凭证（kind + `input_digest` + 批内吸收关系） | 这一条当时看到什么候选池、被判成什么、被谁吸收 |
| trace / token 账本 | 分层调用次数与成本的时间序列 |

## 3. 面与面的冲突（案例原文 §9 的十行）

| # | 冲突 | 已定裁决 |
|---|---|---|
| 1 | 字符帽 vs token 帽 | **两个护栏，不许换算**：字符帽只管传输体积，token 帽只管推理；中文按字符估 token 会低估数倍 |
| 2 | batch 越大越省调用 vs prompt 膨胀 | **封顶**，碎片问题改用批内预收拢 |
| 3 | 分块越多失败半径越小 vs 调用次数越多 | **按字符预算切 + 逐块容错**（失败块留 pending 重投） |
| 4 | 并发越高吞吐越好 vs 子进程单飞 | 远端调用小并发、批量回填单并发；蒸馏 LLM 调用由 `drain()` 单飞天然串行（**没有并发旋钮**） |
| 5 | 单条召回要快 vs 长批要连续 | **priority 只对单条请求生效**（批仍追加队尾） |
| 6 | 熔断窗 vs 自愈窗 | **允许重叠**；**不要**为自愈复位 `failStreak`（会把慢依赖误判成健康） |
| 7 | 自愈要快 vs 毒输入活锁 | **不整批重放 + ack 切片 + 速率窗**；超窗进 failed，显性终局 |
| 8 | 降峰（memPattern）vs 时延（arena 关闭） | 选 **memPattern**（零 infer 代价）；关 arena 只作逃生手段（混合形状下 infer +130~160%） |
| 9 | 收紧上限 vs 配置树安全 | **宽外壁 + 代码内 clamp+warn**，不用窄区间 schema（否则式化配置直接抛错，故障半径是整个配置树） |
| 10 | 观测越全越好 vs 观测自己变成规模问题 | 保留期 + 条数上限（trace 14 天 / token 账本 365 天 / 播报 8 条/轮） |

## 4. 被否决的方案与理由（案例原文 §11）

| 方案 | 否决理由 |
|---|---|
| recycle-on-N（跑 N 轮回收） | 高水位是 `max(T seen)` 的函数、非计数累加器：同形状 24 轮无蠕变；收益≈0，代价是每次 fork+load |
| 降档到 1024 | 不改共存份数 m 只缩 T；已实测的原帽拦住；对语料截断受众 0/1218，却带来 top-5 丢席与口径混叠债 |
| N4 源头截断 | 子侧帽已全覆盖（崩溃面零增益）；装配文本头部截断先丢实质内容 |
| `enableCpuMemArena:false` 默认化 | 混合长度语料 infer +130~160% 时延；只作逃生手段 |
| `global.gc()` / ORT shrinkage env | 证伪：T² 张量由 C++ BFCArena 持有，V8 不可见 |
| 加大去重批 | prompt 线性膨胀（见冲突 2） |
| 为自愈复位 `failStreak` | 会把慢依赖误判为健康 |
| 用窄 schema 区间卡新键 | 配置树抛错的故障半径过大；改宽外壁 + clamp+warn |

## 5. 实测口径与自证边界（案例原环境：Windows / 纯 node）

| 判据 | 结果 | 边界 |
|---|---|---|
| 关内存模式输出等价性 | 三样本 **maxAbsDiff = 0** | 跨进程两臂；等价 ⇒ 不需要重嵌 |
| 关内存模式降峰 | 连发 6 轮 1597MB → 1264MB | 外部轮询；稳态 infer 无回退 |
| 护栏对连发一致性 | 各轮 token 数一致 | 只证预算一致，**不证不崩** |
| 无护栏对照 | 峰值 3.6–3.7GB | 证明护栏在拦真东西 |
| 批内去重收益 | 24 → 23 → 20 条；LLM 调用 2 → 1 | 只减条数/时长，**不降单次峰值** |
| 自愈成本 | ≈2.9s/次 | 速率窗 ≤2 次/60s 的定量依据 |

> **待外部回验（本机不可证）**：① 降峰后 macOS 连发是否仍 SIGTRAP；② 自愈后新进程首轮 trap 概率；③ 报告人语料的 token 分位。
