# DSH 插件多版本线同步：把「两线差异」变成可执行的声明

> 适用场景：插件长期维护两条以上版本线（`main` + 兼容分支），主线持续前进而兼容线落后，
> 需要定期同步，且**兼容线有自己的适配意图不能丢**。

---

## 一、问题：长期并存的两条线一定会漂移

兼容线一旦建立，就同时承受两种力量：

- **主线在前进**：新功能、缺陷修复、文档重写不断落到 `main`。
- **兼容线有自己的意图**：版本序列、`engines` 声明、发布 tag、宿主专属适配。

如果没有机制，"两线差异"就只存在于**某个人的记忆里**。于是每次同步都要重新调研一遍，
而**没有任何东西阻止第三方悄悄多出一点差异**。

本文的方法来自一次真实同步（`dsh-perm-gate`，`main` 领先 `compat/0.1.5` **36 个提交**），
所有数字都是实测。

---

## 二、先量成本，再选做法 —— 不要凭直觉选 `merge`

同步（sync）不是"把 A 合到 B"的同义词。**先测两件事，再决定用哪种做法**。

### 2.1 测「直接 merge 的冲突构成」

```
git merge-tree --write-tree --name-only <兼容分支> main
```

这是**干跑**：不碰工作区、不碰索引、不改 HEAD。实测结果：

| 冲突类别 | 文件数 | 性质 |
|---|---|---|
| `lib/*`（构建产物） | **24** | **纯噪声**——两侧都入库产物，各构建一次就必然冲突 |
| 文档 | 7 | README / CHANGELOG 两侧都重写过 |
| 仓库根规划件 | 3 | 见第五节 |
| 源码 | 3 | 真实冲突 |
| 其它 | 2 | `package.json` 等 |

**38 个冲突里 24 个是产物**。这个比例本身就是结论：**分支形状有问题**，
而不是"冲突很多需要耐心解决"。

### 2.2 测「兼容线到底还剩多少独有价值」

```
git log --oneline main..<兼容分支>            # 独有提交
git ls-tree -r --name-only <兼容分支> > a     # 独有文件（与 main 的树做差集）
git diff main <兼容分支> -- package.json      # manifesto 差异
```

实测收敛到极小：

| 测量 | 结果 |
|---|---|
| 独有提交 | 3 个 |
| 其中「宿主适配」那个提交的独有内容 | **零**——对应文件与测试**全部已在 main** |
| 树中 main 没有的文件 | **仅 2 个** |
| `package.json` 实质差异 | **4~5 个字段** |
| **两侧客户端依赖** | **逐字相同** |

最后一行是决定性的：**两侧的 `@deepseek-ai/dsh-client-*` 版本完全一样**。
也就是说这条兼容线**不是 API 分叉，而是打包＋文档变体**——同步成本因此比直觉低一个量级。

### 2.3 判据

| 若测量结果是 | 那么 |
|---|---|
| 独有内容 ≈ 0，差异集中在 manifest | **树对齐 + 重放 delta**（第三节） |
| 兼容线有若干源码级适配，且与主线改动**不重叠** | 逐个 cherry-pick，分批跑门禁 |
| 兼容线与主线在同一批文件上都有实质改动 | 才轮到 merge（并接受产物冲突） |

## 三、做法：树对齐 + 重放 delta

```
# 1. 在「外部」worktree 里操作，绝不污染主检出
git worktree add -b sync/<线>-from-main <外部目录> <兼容分支>

# 2. 整树对齐到主线（历史保留，兼容线自己的提交不丢）
git -C <外部目录> checkout main -- .

# 3. 移除仓库不该承载的路径（见第五节）
git -C <外部目录> rm -f -q <路径...>

# 4. 重放 delta（只改 manifest）
#    5. 重建产物 + 全量门禁
#    6. 提交 → 推送同步分支 → PR 回兼容线
```

### 3.1 为什么不是 `merge -X ours/theirs`

`-X` 会**静默丢弃**差异。上面测到的 24 个产物冲突之外，还有真实的源码/文档差异；
用 `-X` 掩掉它们，等于用"看起来合完了"换掉"知道合了什么"。

### 3.2 worktree 必须建在仓库**外面**

嵌在主仓库路径下会让 Node 的模块向上解析穿到主仓库的 `node_modules`，
导致重复依赖（同一份 React 装两遍之类）。用同级或完全独立的目录。

### 3.3 产物重建：先比哈希，再决定是否需要

对齐后**先 `build` 一次，再与主线已提交的产物比哈希**：

```
git diff --numstat main -- lib      # 预期为空
```

实测为空 ⇒ 构建确定性成立、两线同源。**这一条比"测试全绿"更有说服力**：
它证明兼容线的产物不是"另一套东西"。

> 反向纪律：如果重建后产物**不一致**，那是环境噪声（换行符、平台、时间戳），
> **应当恢复已提交版本**，而不是把本地重建的产物提交上去污染历史。

## 四、把 delta 声明化：脚本 + 断言

**这是本文最重要的一节。** 树对齐解决了"这一次"，声明化解决"每一次"。

### 4.1 声明什么

```js
export const LINE_015 = {
  branch: 'compat/0.1.5',
  syncedFrom: '42dabae…',          // 钉死的 SHA，见 4.2
  fields: [['version', '3.0.0'], ['description', '…0.1.5 line…']],
  nested: [['engines/node', '>=24'],
           ['engines/dsh', '>=0.1.5-rc.1 <0.2.0-0'],
           ['scripts/release:3x', 'npm publish --tag dsh-0.1.5']],
  absentPaths: ['spec.md', 'tasks.md', 'checklist.md', 'findings.md',
                'patches/add-permissive-glyph.patch'],   // 见第五节
  mirrorPaths: ['package-lock.json'],   // 由 package.json 派生，见 4.4
}
```

配两个子命令：

- `check` —— 校验某个 ref 是否**恰好**只带这些差异，退出码可判。
- `apply` —— 对齐一个 worktree 并重放 delta。**写入前自检**：
  若这次编辑会改动任何**未声明**的路径，直接拒绝写入（防止脚本自己变成漂移源）。

### 4.2 基线必须是**钉死的 SHA**，不能是 `main`

这是最容易做错的地方。若拿"当前的 `main`"当基线：

- 主线一旦前进（加依赖、改版本），兼容线就"看起来漂移了"；
- 而那是**落后**，不是漂移——落后是**预期且允许**的。

于是守卫会在每次主线变动时误报，最后被当成噪声忽略。

**钉死同步点**（`syncedFrom`）才能把两种情况区分开：

| 现象 | 含义 | 处置 |
|---|---|---|
| 与 `syncedFrom` 有**未声明**的差异 | 兼容线被人改过 | **报错** |
| `main` 领先 `syncedFrom` N 个提交 | 兼容线落后 | **提示**，需要时再同步 |

配套纪律：**每次同步完成后，把 `syncedFrom` 更新为本次同步的 `main` 提交**。
声明归主线所有（主线掌握"兼容线应该长什么样"）。

### 4.3 断言守什么、**不**守什么

守（会红）：

- 声明的字段**确实是**声明值；
- 与同步点相比**没有未声明的差异**（这才是防漂移的核心）。注意范围是**整棵树**，
  不只是 `package.json`——见 4.4 第一条坑；
- 不该在仓库里的路径**确实不在**。

**不守**（否则会把两件事绑死）：

- **"线上当前是否已同步"**。那是关于某个分支的运维事实，不是代码属性。
  把它写进单测，会让"这次还没同步"变成主线的红灯——而主线是好的。
  这类问题交给 `check` 的退出码，按需运行。

### 4.4 实践中的坑

- **守卫只读 `package.json`，名字却写着"整棵树"**。第一版 `checkLine` 比对的是两个
  解析后的 `package.json` 对象 + 被追踪路径清单，**全脚本没有任何一处 tree 级 diff**。
  后果：在兼容线上改一个 `src/*.ts`、或换掉 `lib/`，守卫照样退出 0，
  并打印 "carries **exactly** the declared difference"。
  当时的树恰好是对齐的——但那是同步流程（`git checkout main -- .`）保证的，
  **不是任何测试保证的**。
  修法：补一条 `git diff --name-only <syncedFrom> <ref>`，要求差异集合**落在**
  `{package.json} ∪ mirrorPaths ∪ absentPaths` 之内。派生文件（锁文件）必须
  **显式声明**为 `mirrorPaths`，否则它要么被误报成漂移，要么被塞进
  "未声明也不管"的灰色地带。
  教训：**当断言的名字比它的检查范围大，它保护的是错觉。**
- **分隔符必须统一**。声明里写 `engines.node`（点）而检测函数产出 `engines/node`（斜杠），
  会让**合法差异被报成漂移**。我们正是在写测试时撞上这个 bug 的——所以要有测试。
- 断言要覆盖**纯函数**（delta 应用、路径差分、校验），并配**真实的反向控制**
  （拿一个必然不满足声明的 ref 去跑 CLI，断言它**必须**非零退出）。
  否则"绿"可能只是因为它从没检查过任何东西。

## 五、计划文件放哪里：资产 ≠ 产品

> 计划是**过程资产**，不是**产品交付物**。`package.json::files` 从来不包含它们，
> 装到用户机器上的包里没有它们。

实测教训：兼容分支的仓库根目录**躺着它自己的升级计划**（`spec.md` / `tasks.md` /
`checklist.md` / `findings.md`）。同步时若用"整树对齐"，这些文件会被主线的**同名文件**
覆盖——而两者是**两份不同的文档**：

| 文件 | 主线同名文件 | 兼容线文件 | 关系 |
|---|---|---|---|
| `spec.md` | 不存在 | 32 行，兼容线专属决策 | **分支独有** |
| `tasks.md` | 建线记录（18/18 完成） | 升级计划（20 项，5 项未完成） | **同名不同计划** |
| `checklist.md` | 45/45 | 0/24 | 同上 |

**实测两份互不包含**（逐字节比对，各有对方没有的内容）⇒ **都要保留，取一边就是丢数据**。

处置方式：

1. **先字节级复制**到仓库外（workspace 的计划目录），
2. 再从仓库移除，
3. 用 `absentPaths` 断言它们**不会**回来。

### 5.1 判断"这是资产还是陈旧副本"的方法

不要凭文件名和印象。用**逐字节比对**：

```
git rev-parse <分支>:<文件>            # 分支里的 blob
git hash-object <工作区路径>            # 工作区文件的 blob
```

相等 ⇒ 同一份（可以收敛）；不等 ⇒ 先看**两个方向**的差集再决定（很可能要都留）。

## 六、验证清单

同步一轮结束前逐项确认：

- [ ] `git merge-tree` 干跑记录的冲突构成（作为决策依据留档）
- [ ] 独有价值清单（独有提交 / 独有文件 / manifest 字段）
- [ ] 对齐后 `typecheck` / `lint` / `test` / `build` 全绿
- [ ] **重建后的产物与主线已提交产物逐字节一致**（`git diff --name-only <主线> -- lib` 为空）
- [ ] `check` 对同步后的 ref 退出 **0**，并对一个必然不满足的 ref 退出 **非 0**（反向控制）
- [ ] 计划资产已迁出仓库，且 `absentPaths` 断言生效
- [ ] 远端三个 ref 的 SHA 逐一对过（`git ls-remote`）：主线未动、兼容线未动、同步分支新增
- [ ] PR 的落地方式与团队约定一致（PR / 快进）

## 七、反模式

| 反模式 | 为什么坏 |
|---|---|
| 直接 `merge` 长期漂移的兼容线 | 冲突里混着大量产物，真实差异被淹没 |
| 用 `-X ours/theirs` 追求"合完" | 静默丢弃差异，且事后无法审计丢了什么 |
| 拿"当前 `main`"当选同步基线 | 主线一前进就误报漂移，守卫最终被忽略 |
| 把"线上是否已同步"写进单测 | 把分支状态与代码质量绑死，主线红灯却与主线无关 |
| 只写脚本、不写断言 | 脚本省事，断言才防漂移；没有断言，下一次差异照样无人发现 |
| 在主仓库内建 worktree | 模块向上解析穿仓，重复依赖 |
| 重建产物不一致就提交本地版本 | 把环境噪声写进历史 |
| 用同名文件覆盖兼容线的计划记录 | 丢的是**另一份**文档，而且不可逆 |

## 八、适用与不适用

**适用**：兼容线与主线**客户端依赖相同**（即差异是打包/文档层面），
或差异集中在 manifest 与少量文件。

**不适用**（需要另作评估）：

- 兼容线与主线的客户端依赖**不同大版本**——那时差异是 API 层面的，
  树对齐会把主线代码带到一个没有对应依赖的树上。
  先测依赖矩阵，必要时按模块分批重放。
- 兼容线有**与主线改动重叠**的源码适配——树对齐会覆盖它，
  必须先逐项确认哪些适配是"独有的"。

**判断入口始终是第二节的两项测量**，不是直觉。
